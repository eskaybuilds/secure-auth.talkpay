# How this module is wired

Drafted before `create-expo-module` ran, so you know what each generated file is for
before you open it, then corrected against what the SDK 58 template actually produced.
Ownership: Claude scaffolded this; the Swift and Kotlin bodies are yours to write
(learning-mode ADR, "you write, I review").

## What `create-expo-module` generates

`npx create-expo-module@latest` asks for a slug, npm name, native module name, Android
package and author (or takes them as flags), then writes a package from the
`expo-module-template` npm package. It has two modes.

| | Standalone (what we used) | Local (`--local`) |
|---|---|---|
| Where it lives | Its own folder / repo, published to npm | `modules/<name>/` inside one app |
| `package.json` | Full npm package (`main`, `types`, `files`, peer deps) | Minimal, never published |
| Example app | `example/`: an Expo app that links the parent folder | None: the host app is the example |
| Build step | `npm run build` (`tsc`) compiles `src/` → `build/` (JS + `.d.ts`) | None: Metro reads the TS directly |
| Who autolinks it | Any app that installs it from npm or `file:` | The host app, via `modules/` in its autolinking search paths |

Standalone fits because the plan treats secure-auth as its own publishable artefact
(ADR `secure-auth-is-its-own-publishable-repo`). mobile.talkpay consumes it through
`file:../secure-auth.talkpay` until it is published.

### The files that matter

- `expo-module.config.json`: the autolinking manifest. It lists the platforms and the
  native class names to register: `apple.modules: ["SecureAuthModule"]` and
  `android.modules: ["expo.modules.secureauth.SecureAuthModule"]`. At `pod install` or
  Gradle sync, `expo-modules-autolinking` scans `node_modules` for this file and
  generates the registry (`ExpoModulesProvider.swift` on iOS, `ExpoModulesPackageList`
  on Android) that creates your module at startup. If a class name here is wrong, the
  module builds but `requireNativeModule` throws "Cannot find native module".
- `ios/SecureAuth.podspec` + `ios/SecureAuthModule.swift` (+ `SecureAuthRecords.swift`):
  a CocoaPod that depends on `ExpoModulesCore`.
- `android/build.gradle` + `android/src/main/java/expo/modules/secureauth/SecureAuthModule.kt`
  (+ `SecureAuthRecords.kt`): an Android library; `expo-module-gradle-plugin` wires in
  `expo-modules-core`.
- `src/SecureAuthModule.ts`: `requireNativeModule<...>('SecureAuth')`, the single point
  where JS gets hold of the native object. `src/index.ts` is the public API that wraps it.
- `example/`: an Expo app. `package.json` sets `expo.autolinking.nativeModulesDir: ".."`
  so autolinking finds the module in the parent folder, `metro.config.js` adds `..` to
  `watchFolders`, and `app.json` turns on `experiments.autolinkingModuleResolution` so
  Metro resolves the import to it. `example/ios` and `example/android` are generated by
  prebuild and gitignored. You test native changes here with `npm run ios` / `npm run android`.
- `internal/module_scripts/`: small Node scripts behind `build`, `clean`, `test`,
  `prepare` and `open:ios` / `open:android`. Older templates used the `expo-module-scripts`
  package (`expo-module build`) for this; the SDK 58 template inlines it and drives plain
  `tsc` with `tsconfig.json` (which extends `expo/tsconfig.base`).
- The published `expo-module-template@58.0.9` is missing its `tsconfig.json` (its own
  `.npmignore` excludes it), so `npm install`'s `prepare` step failed. This repo was
  scaffolded from a local copy of the template with a `tsconfig.json` added (`--source`).

## The Swift side: a `Module` with a definition DSL

```swift
public class SecureAuthModule: Module {
  public func definition() -> ModuleDefinition {
    Name("SecureAuth")                       // the name JS passes to requireNativeModule

    AsyncFunction("getSecret") { (key: String, options: GetSecretOptions, promise: Promise) in
      promise.reject("NOT_IMPLEMENTED", "...")  // or resolve(value)
    }
  }
}
```

`definition()` uses a Swift result builder: each call (`Name`, `Function`,
`AsyncFunction`, `Constants`, `Events`, `OnCreate`, `View`) declares part of the module.
Expo reads the closure's parameter types and converts JS values into them for you
(`String`, `Bool`, `[String: Any]`, or a `Record` struct with `@Field` properties). If
the conversion fails, the promise rejects before your code runs. Use `AsyncFunction` for
anything that might show UI or block, such as Keychain reads behind Face ID. It returns
a JS Promise, and you settle it with `promise.resolve` / `promise.reject(code, message)`
or by throwing an `Exception`.

## The Kotlin side: same DSL, Kotlin syntax

```kotlin
class SecureAuthModule : Module() {
  override fun definition() = ModuleDefinition {
    Name("SecureAuth")

    AsyncFunction("getSecret") { key: String, options: GetSecretOptions, promise: Promise ->
      promise.reject("NOT_IMPLEMENTED", "...", null)
    }
  }
}
```

`appContext.reactContext` gives you a `Context`, and `appContext.currentActivity` gives
you the `FragmentActivity` that `BiometricPrompt` needs. Records are classes that
implement `Record` and use `@Field`.

Both platforms register under the same `Name`, so JS calls one module whichever OS it
runs on. Keeping the function names, argument shapes and error codes identical across
the two platforms is your job; `src/SecureAuth.types.ts` is the contract.

## Where this sits on the New Architecture

```
JS (Hermes)  ── requireNativeModule('SecureAuth') ──▶  JSI host object
                                                        │  (installed by expo-modules-core)
                                                        ▼
                                  ExpoModulesCore: argument conversion, promises, threading
                                                        │
                                       ┌────────────────┴────────────────┐
                                       ▼                                 ▼
                             SecureAuthModule.swift             SecureAuthModule.kt
```

- **JSI** (JavaScript Interface) is the C++ API that lets the JS engine hold direct
  references to native objects and call them synchronously. There is no JSON bridge
  and no batched message queue.
- **TurboModules** are React Native's own JSI-based native modules. You write a typed
  JS spec, and **Codegen** generates C++/ObjC/Java glue from it.
- **The Expo Modules API** is a separate system built on the same JSI layer. It does
  not use Codegen specs. At startup `expo-modules-core` installs one JSI object
  (`globalThis.expo.modules`), and each registered module appears as a host object on
  it. Calls go JS → JSI → ExpoModulesCore (C++ / Swift / Kotlin) → your closure. The
  DSL takes the place of the Codegen spec, which is why there is no `NativeSecureAuth.ts`
  spec file here.
- **Trade-off:** the JS types are written by hand (`SecureAuth.types.ts`), not generated
  from a spec, so the compiler cannot catch a TS/native signature mismatch. A wrong type
  becomes a runtime conversion error. In return you get one ergonomic DSL in Swift and
  Kotlin, and you don't have to write any C++ or ObjC++.
- **Fabric** (the new renderer) only matters for native *views*. This module has none:
  it was scaffolded with `--features AsyncFunction` only, so no `View` files were generated.

## Interview questions this answers

1. Why an Expo module rather than a bare TurboModule? (Same JSI performance; the Swift
   and Kotlin DSL takes the place of Codegen and the C++ glue; works in any Expo or bare
   RN app with autolinking.)
2. What does `expo-module.config.json` do, and what breaks if a class name in it is wrong?
3. How does a native `promise.reject("LOCKED_OUT", …)` reach JS as `error.code === 'LOCKED_OUT'`?
